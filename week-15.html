A Flutter Entry Point, Four Camera Boxes, and a gRPC Control Plane

Sep 1 – Sep 7, 2026 Abdulrahman

This week

  • Scaffolded the Flutter front-end (flutter-surround-view), with the entry point modelled on AGL's own camera_streams_app demo — WidgetsFlutterBinding.ensureInitialized() then runApp(). Builds and runs on Linux desktop, ready to retarget to flutter-auto on AGL.
  • Built the first screen: a 2×2 camera grid, each quadrant a CameraBox (placeholder image now, a Texture later) that switches to a single feed or a bird's-eye placeholder.
  • Added the control chrome — a full-height left rail (overlay toggles, snapshot, calibrate, settings) and a bottom bar (6-way view-mode segmented control + a backend-link status pill) — wired as a clickable mock driven by local state.
  • Built the calibration panel — camera select + X / Y / Yaw nudge buttons + Save / Reset — as the UI face of the cam_x/cam_y/yaw live-tune already in the C++ renderer.
  • Designed the UI↔backend boundary: two processes, gRPC over a Unix domain socket, the backend owning the authoritative state and the UI rendering from a WatchState stream. Drafted the .proto.

Details

The entry point

Rather than invent a structure, I looked at what AGL's Flutter demos actually do. The camera_streams_app in the meta-agl-demo layers has the minimal shape: an async main that makes sure the Flutter bindings exist before any plugin or async work runs, then hands a single root widget to runApp. Mine is the same, minus the camera-plugin line it has and I don't need yet: 

Future<void> main() async {
  WidgetsFlutterBinding.ensureInitialized();
  runApp(const SurroundViewApp());
}

class SurroundViewApp extends StatelessWidget {
  const SurroundViewApp({super.key});

  @override
  Widget build(BuildContext context) {
    return MaterialApp(
      title: 'Surround View',
      theme: ThemeData.dark(),
      home: const SurroundViewScreen(),
    );
  }
}

Nothing in the Dart entry point is AGL-specific. The "AGL" part lives entirely in the Yocto recipe — inherit flutter-app agl-app, a PUBSPEC_APPNAME, a systemd unit, and flutter build bundle against the flutter-auto embedder. The same main.dart runs on a desktop or on the target; only the embedder and the build tooling change. That recipe doesn't exist yet — for now the app builds as a plain Flutter Linux desktop app so the layout is fast to iterate on.

Four boxes

The first screen is a Column of two Rows, every child wrapped in Expanded, so each quadrant is exactly a quarter of the window and resizes with it. Each cell is a CameraBox: a bordered container holding Image.asset today, with an errorBuilder fallback so a missing file shows a placeholder instead of a red error box.

When the capture pipeline is wired in, the Image.asset becomes Texture(textureId: …) — a plugin registers an external texture with the engine and feeds it frames from the libcamera / DMA-BUF output, no CPU copy. The 2×2 layout and the CameraBox wrapper don't change; only the child of the Stack swaps.

The control chrome: a left rail and a bottom bar

The bottom bar is a 6-way view-mode segmented control: Grid shows the 2×2, Front / Rear / Left / Right each show one feed full-screen, BEV shows the stitched-view placeholder. The left rail carries the overlay toggles (guide lines, distance grid), snapshot, calibrate, and settings. The ● mock pill at the right end is a placeholder for the gRPC link status.

Structurally it's deliberately plain: one StatefulWidget holds all the state (view mode, active overlays, calibration flag and deltas), and everything below it is stateless and presentational. Props flow down, callbacks flow up, one setState per interaction. Each of those callbacks is exactly where a gRPC request call goes later.

The calibration panel

The Calibrate button reveals a small panel over the viewport: four camera chips, then X / Y / Yaw rows each with a − and a +, then Save and Reset. The nudges accumulate and show live (x 0.0  y 0.0  yaw 0.0°). This is the UI face of the live-tune that already exists on the C++ side — the cam_x_delta / cam_y_delta / yaw_delta fields from the week the 'W' save key was overwriting its own baseline. The panel doesn't do the maths; it just sends deltas.

How the buttons will talk to the pipeline

The buttons are the easy 10%. The real question is the transport. First fork: one process or two? That's decided by how the camera pixels and the Flutter chrome end up on the same screen — the C++ renderer keeping its own Wayland surface with the Flutter UI drawn transparent on top, versus the C++ output becoming a Flutter external texture. The renderer already runs standalone with its own EGL / Wayland window, so two processes is the natural next step.

For the channel between them I settled on gRPC over a Unix domain socket. The .proto is a contract that documents the whole control surface; one server-streaming RPC gives the "backend owns the state" model for free; and there's a reference in-tree — the same camera_streams_app talks to its inference service exactly this way. A Unix socket, not a TCP port: the backend runs as a systemd service with /dev/video* access, the UI runs unprivileged and After= it. 

service SurroundView {
  rpc SetViewMode  (ViewModeRequest)  returns (State);
  rpc SelectCamera (CameraRequest)    returns (State);
  rpc SetOverlay   (OverlayRequest)   returns (State);
  rpc Calibrate    (CalibrateRequest) returns (State);
  rpc Snapshot     (SnapshotRequest)  returns (SnapshotReply);
  rpc WatchState   (Empty)            returns (stream State);   // backend -> UI
}

The important design choice is state the backend owns, not fire-and-forget commands. The UI sends a request to change state; the backend broadcasts the new state; every widget renders from the broadcast. The UI is not the only input — reverse gear (CAN → KUKSA.val / VSS) auto-selects the rear camera, a calibration script can poke the deltas, a second client can connect. If the UI rendered from its own optimistic guesses it would drift; rendering from one authoritative stream keeps it honest.
