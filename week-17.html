Live Cameras to the GPU, and Into Flutter Through ivi-homescreen

Sep 15 – Sep 21, 2026 Abdulrahman

This week

  • Reworked the live camera path into a reusable pipeline that opens every camera libcamera reports, one capture slot per camera, and fixed a missing validate() call before configure() that the renderer's stride depends on
  • Added a live multi-camera path to the GPU renderer: a new shader that samples each camera's DMA-BUF directly as an external texture, so two live cameras blend into the same BEV canvas the recorded videos produced
  • Ran it on the RPi5 with two IMX219 cameras and fixed a Mesa V3D driver crash on the first draw by declaring one external sampler per camera instead of an array of samplers
  • Exposed the pipeline as a C API in libpipeline_core.so (create, start, stop, calibration, snapshot) with its own render thread and EGL context, plus a small test program to check it on the board
  • Found why cross-building from the PC against a copied Pi sysroot failed (an older host toolchain against Trixie's glibc) and moved to building the library natively on the Pi
  • Set up emb_cli and built ivi-homescreen for the Pi 5 with emb cross: pinned the right Flutter version, initialised the missing submodules, and turned on BUILD_COMPOSITOR so the shell hosts platform views
  • Built ivi-homescreen and the Flutter app for the Pi 5 with emb cross, and ran the platform view from a PC over SSH, including working through emb setup problems (PATH, Flutter version pin, submodules, a full disk, missing arm64 engine tools)
  • Tested Joel's pull request on the Pi with the test pattern and with live cameras. Two cameras ran at 30 fps once the sensors' frame duration was pinned with the camera_fps flag (the limit was the sensors' auto exposure, not the GPU), and the zoom and size were tuned with BEV_PX_PER_M, BEV_WIDTH, BEV_HEIGHT, BEV_CAM_FPS and BEV_CAMERAS
  • Moved my Flutter UI onto Joel's bev_view package and merged it into main locally: the 360 view is now a live two-camera blend shown through his platform view, running on the Pi 5
  • Added live single-camera views for front and right, each as the normal image or as that camera's own bird's-eye view, and made the Front/Rear toggle use them too. Rear, left and the 2D view are still placeholders
  • Added the frame rate readout to every live view (on screen with BEV_STAT=1, and as a console line on the 360 view), using Joel's stats: fps, source and view size, buffer type, fence waits
  • Fixed the single-camera shader to output the true camera colors, gave each camera:N source its own calibration slot, and added a short retry when a camera is still busy while one view closes and the next opens
  • Set up a repeatable deploy loop from the PC: rsync the source to the Pi, rebuild the library there, run emb cross with --deploy-dir, copy the native libbev_view.so over the bundled one, and start the app over SSH with the Wayland environment

Details

The path from a camera to a Flutter view

Two live cameras are opened by libcamera and their DMA-BUFs are imported straight into the GPU, where a shader blends them into the bird's-eye-view canvas. The result is handed to ivi-homescreen as a platform view through Joel's delivery code, and the Flutter app shows that view. Nothing is copied through the CPU on the way.

What was built

  • A multi-camera pipeline (pipeline_runtime) that opens every camera libcamera reports.
  • A live blend path in the renderer, plus a linear export ring for the shell.
  • A C API in libpipeline_core.so with its own render thread and EGL context, and a small test program for the board.
  • A full emb cross build and deploy of the shell and the app to the Pi 5.
  • A read-through of Joel's pull request, and running its example on the board as a reference.

Building ivi-homescreen and the app with emb

The commands in the order I ran them, with the problem each one hit and how it was solved. Everything runs on the PC, and emb cross builds for the Pi 5 and copies the result over SSH.

1. Get emb into the shell

cd /media/abdu/LinuxHome/Embedded_Linux/git_ignoring/gsoc/emb_cli
eval "$(./bootstrap.sh --shellenv)"
emb --version

Problem: emb: not found. The command is only on the PATH after the bootstrap script prints its environment. Fix: run the eval line in every new terminal.

2. Move the cache to the big disk

export EMB_CACHE_DIR=/media/abdu/LinuxHome/emb-cache
echo 'export EMB_CACHE_DIR=/media/abdu/LinuxHome/emb-cache' >> ~/.bashrc

Problem: the sysroot build failed with dd failed: No space left on device. The default cache is on the small system disk. Fix: point EMB_CACHE_DIR at the bigger disk, delete the half-written temporary files, and start again.

3. Set up the toolchain and Flutter

emb doctor
emb setup --config ../configs --yes
. ./setup_env.sh

Problem: the setup did not use the Flutter version ivi-homescreen expects. Fix: read it from the shell's own .flutter-version file and pass it in. 

cat ../ivi-homescreen/.flutter-version
emb setup --skip-deps --skip-sync --arch arm64 --flutter-version "$(cat ../ivi-homescreen/.flutter-version)"
. ./setup_env.sh
flutter --version

4. Initialise the shell's submodules

cd /media/abdu/LinuxHome/Embedded_Linux/git_ignoring/gsoc/ivi-homescreen
git submodule update --init --recursive

Problem: the shell build failed because several submodule folders were empty. Fix: the command above.

5. Build the arm64 engine

cd /media/abdu/LinuxHome/Embedded_Linux/git_ignoring/gsoc/emb_cli
. ./setup_env.sh
emb engine --arch arm64 --mode release

Problem: the release build of the app could not find an arm64 gen_snapshot. Fix: build the arm64 release engine, which provides it.

6. Turn on the compositor for wayland-egl

Problem: the app started, but the platform view failed with MissingPluginException on flutter/platform_views. The shell only registers that handler when built with BUILD_COMPOSITOR, and the Pi manifest had it off for the wayland-egl backend. Fix: add it under wayland-egl in ivi-homescreen/.emb/raspberry-pi.emb.yaml and rebuild the shell. 

wayland-egl:
  BUILD_COMPOSITOR: 'ON'

7. Build and deploy the shell and the app

cd /media/abdu/LinuxHome/Embedded_Linux/git_ignoring/gsoc/emb_cli
eval "$(./bootstrap.sh --shellenv)"
. ./setup_env.sh
emb cross /media/abdu/LinuxHome/Embedded_Linux/git_ignoring/gsoc/ivi-homescreen \
  --target rpi5-trixie --build --backend wayland-egl --no-verify \
  --app /media/abdu/LinuxHome/Embedded_Linux/git_ignoring/gsoc/libcamera-dmabuf-capture/flutter-surround-view \
  --mode release --deploy abdu@192.168.100.23 --deploy-dir ui

This builds the shell, bundles the Flutter app, and copies both into ~/ui on the Pi. Problem: the deployed libbev_view.so was cross-built against libcamera 0.4, but the Pi runs 0.7, so it would not load. Fix: rebuild the library on the Pi and copy it over the bundled one after every deploy. 

ssh abdu@192.168.100.23 'cp ~/libcamera-dmabuf-capture-live/build-pi/libbev_view.so ~/ui/lib/libbev_view.so'

8. Run it on the Pi

ssh -t abdu@192.168.100.23 'cd ~/ui && BEV_STAT=1 WAYLAND_DISPLAY=wayland-0 XDG_RUNTIME_DIR=/run/user/$(id -u) ./homescreen -b . -f'

Where we stand

The Flutter app runs on the Pi 5 through ivi-homescreen with two live cameras at 30 fps. It shows a live 360 view, plus live front and right views as normal or bird's-eye, each with an fps readout. Rear, left and the 2D view are still placeholders. Open points are the release fences, which never signal on the wayland-egl backend (every frame waits its 34 ms and draws over the buffer anyway), calibrating the config for the live rig, and the runtime controls (zoom and calibration), which the app does not have yet.

Getting the Pi's screen onto the tablet
