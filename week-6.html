Week 6 — Fixing the RPi5 U-Boot First-Boot Hang

Jun 30 – Jul 6, 2026 Abdulrahman

This week

  • Identified the root cause of the RPi5 U-Boot hang: saveenv (FAT write) freezes on first boot because U-Boot's FAT write driver is broken with the RP1 south bridge I/O chip
  • Fixed it with a single build-time addition to rpi-config_git.bbappend: pre-create a valid empty uboot.env so boot.scr never calls saveenv on first boot
  • Confirmed U-Boot 2026.01 can load the 27 MB kernel Image from FAT without issue — the hang was only saveenv, not the kernel load
  • Verified end-to-end: build → flash → first boot → Linux desktop — no manual intervention required
  • Downloaded and ran surround-view-system-introduction (neozhaoliang) — a complete Python/OpenCV surround-view pipeline with BEV projection, homography calibration, and multi-camera blending; studied its approach as a reference for the AGL backup camera stitching stage

Details

Recap: where week 5 left off

Last week the RPi5 booted by adding kernel=Image to config.txt, which tells the BCM2712 firmware to load Linux directly and skip U-Boot entirely. That got the board running, but it is a bypass, not a fix — U-Boot is supposed to be in the boot chain. This week's goal was to understand exactly why U-Boot hangs on first boot and apply the smallest possible fix at the build level.

The RP1 south bridge and what it means for U-Boot

The RPi5 introduced an RP1 I/O chip connected to the BCM2712 SoC via PCIe. Almost everything that is not the CPU — SD card, USB, GPIO UART, Ethernet — is routed through RP1. Linux has a full RP1 driver and works perfectly. U-Boot, however, only brings up the drivers it explicitly supports, and its FAT write path over RP1 is broken in 2026.01.

This matters because of what happens on the very first boot. The AGL boot.scr contains this guard: 

if test ! -e mmc 0:1 uboot.env; then saveenv; fi

When the board is first flashed, uboot.env does not exist on the FAT partition. So U-Boot calls saveenv, which writes the env block to the FAT partition via the RP1 MMC controller — and hangs indefinitely. The kernel load that follows never happens.

Importantly, the FAT read path and the kernel load are both fine. U-Boot 2026.01 can fatload the 27 MB Image at full speed — the hang is only the FAT write inside saveenv.

The fix — pre-create uboot.env at build time

The boot.scr guard only calls saveenv if uboot.env is absent. The fix is simply to generate a valid env image at Yocto build time and include it in the boot partition, so the file is present from the very first boot and the saveenv call is skipped entirely.

A valid U-Boot env image is a 16 kB block: a 4-byte CRC32 over the env content, two null bytes (the empty-env marker), padded to 16 kB with 0xFF. Because the env content is just the two null bytes, U-Boot reads this file, finds an empty env, and falls back to its compiled-in defaults for every variable — bootcmd, kernel_addr_r, bootdelay, everything. No variables are lost.

This was added to rpi-config_git.bbappend as a single new task: 

do_deploy:append:raspberrypi5() {
    python3 -c "
import struct, zlib, sys
env = b'\x00\x00' + b'\xff' * (0x4000 - 4 - 2)
crc = zlib.crc32(env) & 0xFFFFFFFF
sys.stdout.buffer.write(struct.pack('<I', crc) + env)
" > ${DEPLOYDIR}/bootfiles/uboot.env
}

The file is placed in DEPLOYDIR/bootfiles/, which is the directory that rpi-config already uses to populate the FAT boot partition in the WIC image. No packaging changes or extra recipes are needed.

Confirming the fix with UART

The RPi5 debug UART — the one U-Boot actually uses — is a 3-pin JST SH 1.0mm connector located between the two HDMI ports. It is wired directly to the BCM2712 SoC and is available from the very first U-Boot instruction. The GPIO UART (pins 14/15) goes through RP1, which U-Boot never initialises, so it is silent during the entire U-Boot stage.

With a serial adapter connected to the JST SH port, the UART output after the fix shows U-Boot loading boot.scr, detecting that uboot.env exists, skipping saveenv, running fatload for the kernel, and handing off to Linux — first boot, no hang.

Challenges & learnings

Challenge

No UART output from U-Boot made it hard to pinpoint where the hang occurred without the JST SH connector. Every hypothesis had to be tested by reflashing and watching whether the board reached the Linux desktop or stopped at the U-Boot splash. Once the UART was connected, the culprit — saveenv — was immediately visible in the logs.

Key learning

A pre-created env file with a valid CRC but no variables is treated by U-Boot as "env exists, nothing to restore" — all compiled-in defaults remain active. This means the fix is completely transparent to the rest of the boot: no variables need to be duplicated or maintained in the generated file.
