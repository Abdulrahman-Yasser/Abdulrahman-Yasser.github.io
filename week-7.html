Trying to understandthe math behind

I tried to understand the math behind the IPM (Inverse Perspective Mapping) and how to implement it in the shader, which took a lot of time, but I think I unerstand it now !

One matrix per camera, backward mapping

ground_to_image_H() builds a homography H such that for any BEV pixel p = (px, py, 1): 

s  = H * p
uv = (s.x / s.z, s.y / s.z)   // camera image coordinate, already in [0,1]

This is backward mapping — for every output pixel, ask where to sample from — which is the standard approach for GPU warps because it guarantees every output pixel gets filled, with no holes. H is built once per camera at startup (or whenever a calibration parameter changes) and never touched per-frame; the shader (not yet written) will just do one matrix-vector multiply and a perspective divide per fragment.

Coordinate conventions

World/ground frame: X right, Y forward, Z up, ground at Z=0. The two cameras sit at (cam_x, cam_y, h), differing only in cam_x = ∓baseline/2. Camera frame follows the standard pinhole convention: X right, Y down, Z forward (depth). The BEV canvas is (px, py) pixels with a top-origin convention — py=0 is the far/top row, like a normal image — which turns out to matter later.

Two deliberate deviations from the spec

No inverse

The original task write-up called for H = inverse(P * M), where M maps a BEV pixel to its ground point and P maps a ground point to the camera image. By plain matrix associativity, P * (M * p) = (P * M) * p — so P*M already is the direct BEV→image mapping the shader needs. Inverting it would flip the mapping to image→BEV, which is backwards for a shader doing H * bevPixel per fragment. The likely origin of the "inverse" step: OpenCV's cv2.warpPerspective expects a src→dst matrix and inverts it internally to do the backward sampling — this project doesn't use OpenCV, so the GLSL shader will do that backward sampling "by construction," and inverting again would be a double-inversion bug. The mat3::inverse() method (and its unit self-test, also in the original spec) was dropped entirely and replaced with a startup sanity check instead (next section).

Extended signature

The spec's function signature only took (cam_x, cam_y, h, pitch_deg, yaw_deg, K) — but building M needs px_per_m, bev_w, bev_h, none of which are derivable from those. And K uses pixel-unit intrinsics, so P*M naturally comes out in pixel units, while the eventual shader's validity check assumes normalized [0,1] UV. The fix: extend the signature with img_w, img_h (passed explicitly by the caller — not recovered from K — since the caller already has the decoded frame size) plus px_per_m, bev_w, bev_h, and normalize H's rows by img_w/img_h inside the function itself, so the shader needs no normalization logic of its own.

Verifying it without touching hardware

ipm.cpp has zero GL/libcamera dependencies, so it compiles as a standalone program on a plain dev machine: 

g++ -std=c++17 -DIPM_STANDALONE_TEST ipm.cpp -o /tmp/ipm_test -lm && /tmp/ipm_test

Three checks came out of that:

  • Straight down (pitch=-90, camera over the world origin): the BEV center projects to image uv (0.500, 0.500) — exactly the principal point, as it must be for this degenerate case.
  • Default config (baseline 0.40 m, height 1.2 m, pitch -30°): left and right cameras give mirror-symmetric uv at the shared centerline (0.776 vs. 0.224).
  • Vertical centerline sweep: depth (z) starts positive and inside the image for far ground, then crosses zero and goes negative (invalid/behind-camera) for near/behind-rig points — monotonic, no accidental sign flip.

Also added ipm_debug_check(), meant to run once per camera at real startup: it projects the BEV canvas center through H and prints whether the result lands inside [0,1], so a sign or axis mistake shows up immediately as OUTSIDE image! in the log instead of a silent black or garbled render on the Pi.

Challenges & learnings

Key learning

Matrix associativity — P*(M*p) = (P*M)*p — means the composed homography is already the backward mapping a GPU shader needs; inverting it on top silently double-inverts. Also: build correctness checks (ipm_debug_check, the standalone g++ test) before touching GLES at all, since a homography sign error on real hardware looks identical to a black screen or a camera fault — much harder to debug once GL, EGL, and libcamera are all in the mix too.
