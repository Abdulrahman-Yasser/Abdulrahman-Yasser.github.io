Week 3: DMA-BUF into the GPU, First Shader, Parking Grid

Jun 9 – Jun 15, 2026 Abdulrahman github: libcamera-dmabuf-capture

This week

  • Set up a headless EGL context via GBM + DRM render node — no display server, no X11, no Wayland compositor needed to drive the GPU
  • Imported the camera DMA-BUF fd directly into the GPU as a GL_TEXTURE_EXTERNAL_OES via eglCreateImageKHR with EGL_LINUX_DMA_BUF_EXT — zero-copy path confirmed working on the RPi4
  • Wrote GLSL ES 3.0 shaders: Mesa V3D does NV12→RGB conversion in hardware on the sampler path, so the fragment shader receives RGB directly. Added a red tint and a parking guide grid overlay (3 horizontal + 2 vertical lines)
  • Rendered to an offscreen FBO and saved the result to /tmp/frame.png via libpng — verified the image is visually correct (correct colors, correct orientation, grid lines visible)
  • Refactored CaptureSession into its own header and source files; added capturedBuffer() so the DMA-BUF can be handed off to the GPU stage after capture
  • Switched the build to the AGL SDK (suggested by the mentors): bitbake -c populate_sdk generates a proper SDK, then cmake -DCMAKE_TOOLCHAIN_FILE="$CMAKE_TOOLCHAIN_FILE" replaces the old manual cross-build.sh script

Details

Why headless

At this stage there is no Wayland compositor running and no display output wired up yet. The goal this week was to verify that the full GPU path works end to end — DMA-BUF in, pixels out — before tackling the display side. Running headless keeps the scope small: one render, read the pixels back, save as PNG, check visually.

The glReadPixels readback is explicitly a debug path and is marked to be removed in Stage 4. Once the pipeline drives a real Wayland surface there is no need to ever pull pixels back to the CPU.

GBM + DRM render node

The entry point is /dev/dri/renderD128, the DRM render node for the V3D GPU on the RPi4. Render nodes are unprivileged — no root, no display manager, no KMS/modesetting needed. The flow is:

  1. Open /dev/dri/renderD128 with O_RDWR | O_CLOEXEC
  2. Wrap the fd with gbm_create_device — GBM is Mesa's generic buffer manager, the layer that lets EGL work without knowing whether it's on X11, Wayland, or nothing at all
  3. Get an EGL display via eglGetPlatformDisplayEXT(EGL_PLATFORM_GBM_MESA, gbm_dev, NULL)
  4. Initialize EGL, choose a GLES2-capable config, create a GLES 3.0 context
  5. Call eglMakeCurrent(dpy, EGL_NO_SURFACE, EGL_NO_SURFACE, ctx) — surfaceless context, no window needed

EGL_KHR_surfaceless_context is checked before the MakeCurrent call. The V3D driver on the AGL RPi4 image supports it.

Importing the DMA-BUF

eglCreateImageKHR, eglDestroyImageKHR, and glEGLImageTargetTexture2DOES are KHR/OES/EXT extension functions. They are not guaranteed to be exported symbols from libEGL.so, so they cannot be linked normally. They must be resolved at runtime: 

pfn_CreateImage = (PFNEGLCREATEIMAGEKHRPROC)
    eglGetProcAddress("eglCreateImageKHR");

The EGLImage is created from the DMA-BUF fd that libcamera handed back last week. The NV12 format has two planes in a single fd — Y at offset 0 and UV at offset 2049920. Both planes go into one eglCreateImageKHR call using EGL_LINUX_DMA_BUF_EXT: 

const EGLint attrs[] = {
    EGL_WIDTH,                     1640,
    EGL_HEIGHT,                    1232,
    EGL_LINUX_DRM_FOURCC_EXT,      DRM_FORMAT_NV12,
    EGL_DMA_BUF_PLANE0_FD_EXT,     fd,
    EGL_DMA_BUF_PLANE0_OFFSET_EXT, 0,
    EGL_DMA_BUF_PLANE0_PITCH_EXT,  1664,
    EGL_DMA_BUF_PLANE1_FD_EXT,     fd,
    EGL_DMA_BUF_PLANE1_OFFSET_EXT, 2049920,
    EGL_DMA_BUF_PLANE1_PITCH_EXT,  1664,
    EGL_NONE,
};

The EGLImage is then bound as GL_TEXTURE_EXTERNAL_OES using glEGLImageTargetTexture2DOES. This is the texture type required for EGLImages — you cannot use GL_TEXTURE_2D for an imported DMA-BUF.

NV12 to RGB — hardware, not shader math

On Mesa V3D (the RPi4 GPU driver), binding an NV12 EGLImage as GL_TEXTURE_EXTERNAL_OES and sampling it with samplerExternalOES gives you RGB values directly. The driver performs the YCbCr-to-RGB conversion in hardware on every texture fetch. The fragment shader does not need to implement the BT.601 matrix manually.

The extension needed in the shader is GL_OES_EGL_image_external_essl3 (the ESSL3 variant, not the ESSL1 one) because the shaders target #version 300 es.

The shaders

The vertex shader uses a trick to avoid allocating a VBO: it drives a single oversized triangle from gl_VertexID. One glDrawArrays(GL_TRIANGLES, 0, 3) call covers the entire viewport with no buffer setup: 

#version 300 es
out vec2 vTexCoord;
void main() {
    const vec2 pos[3] = vec2[3](
        vec2(-1.0, -1.0),
        vec2( 3.0, -1.0),
        vec2(-1.0,  3.0)
    );
    vTexCoord   = pos[gl_VertexID] * 0.5 + 0.5;
    gl_Position = vec4(pos[gl_VertexID], 0.0, 1.0);
}

The fragment shader flips Y (DMA-BUF origin is top-left, GL UV origin is bottom-left), applies a red tint (boost red channel, suppress green and blue), then draws a parking guide grid using step to avoid branching: 

#version 300 es
#extension GL_OES_EGL_image_external_essl3 : require
precision mediump float;
uniform samplerExternalOES uTexture;
in  vec2 vTexCoord;
out vec4 fragColor;
void main() {
    vec2 uv  = vec2(vTexCoord.x, 1.0 - vTexCoord.y);
    vec3 rgb = texture(uTexture, uv).rgb;

    vec3 tinted = vec3(min(rgb.r * 1.5, 1.0), rgb.g * 0.5, rgb.b * 0.5);

    float lw = 0.005;  /* ~6 pixels on a 1232-tall image */
    float h1 = 1.0 - step(lw, abs(uv.y - 0.25));
    float h2 = 1.0 - step(lw, abs(uv.y - 0.50));
    float h3 = 1.0 - step(lw, abs(uv.y - 0.75));
    float v1 = 1.0 - step(lw, abs(uv.x - 0.33));
    float v2 = 1.0 - step(lw, abs(uv.x - 0.66));
    float grid = max(max(max(h1, h2), max(h3, v1)), v2);

    fragColor = vec4(mix(tinted, vec3(1.0), grid), 1.0);
}

Offscreen FBO and PNG readback

Without a window surface, rendering goes into a GL_RGBA8 renderbuffer attached to an FBO. After glDrawArrays and glFinish, glReadPixels pulls the result back to CPU memory. OpenGL returns rows bottom-to-top, but PNG expects top-to-bottom, so the rows are written to libpng in reverse order.

This CPU readback is the only part of the pipeline that is not zero-copy. It exists only to visually confirm the shader output is correct. In Stage 4 it will be removed and the rendered FBO will be shared directly with the display compositor via DMA-BUF export.

Switching to the AGL SDK build

The mentors at AGL suggested dropping the manual sysroots-components approach and using bitbake -c populate_sdk instead: 

bitbake <someimage>
bitbake -c populate_sdk <someimage>

This installs a proper relocatable SDK under /opt/agl-sdk/. The environment-setup script it provides sets $CMAKE_TOOLCHAIN_FILE and all the cross-compiler variables, so the build is just: 

source /opt/agl-sdk/21.90.0-aarch64-agl-image-flutter-debug/environment-setup-aarch64-agl-linux
mkdir -p build && cd build
cmake -DCMAKE_TOOLCHAIN_FILE="$CMAKE_TOOLCHAIN_FILE" ..
make -j$(nproc)

This replaces the old cross-build.sh script that was manually patching broken symlinks left by rm_work.

Challenges & learnings

Challenge

eglCreateImageKHR and glEGLImageTargetTexture2DOES are not exported symbols from libEGL.so — trying to call them directly gives a linker error or a null pointer crash. Every EGL/GL extension function that isn't in the core must be resolved at runtime via eglGetProcAddress. Also: Mesa V3D rejected two-component DRM formats (e.g. RG88) for EGLImage — the format must be DRM_FORMAT_NV12 with both planes declared in the attribute list.

Key learning

Mesa V3D performs NV12→RGB conversion in hardware on the samplerExternalOES sampler path — no BT.601 matrix in the shader needed. Also: GL_TEXTURE_EXTERNAL_OES is not optional for EGLImages; GL_TEXTURE_2D will silently fail. And the oversized-triangle trick (gl_VertexID + no VBO) is a clean way to do fullscreen rendering in GLES 3.0 without any buffer setup.
