Week 5 — Building & Booting AGL on RPi4 and RPi5

Jun 23 – Jun 29, 2026 Abdulrahman

This week

  • Rebuilt agl-ivi-demo-flutter for RPi4 from scratch — diagnosed why the camera was not working in the previously built agl-image-flutter-debug image and switched to the correct image recipe
  • Fixed RPi4 camera support at the build level — added RASPBERRYPI_CAMERA_V2 = "1" to local.conf (adds dtoverlay=imx219 to config.txt) and committed PROVIDES += "libcamera" to rpi-libcamera so PREFERRED_PROVIDER_libcamera resolves correctly
  • Built and flashed agl-ivi-demo-flutter-raspberrypi5 — debugged first-boot failures caused by two issues in the AGL image configuration
  • Identified root cause of RPi5 boot freeze: kernel_2712.img on the boot partition is U-Boot, which hangs on saveenv on first boot — fixed by setting kernel=Image in config.txt to bypass U-Boot entirely
  • Fixed kernel console output on RPi5 — kernel logs were routed to UART only (console=serial0,115200); added console=tty0 so boot messages appear on HDMI
  • Committed both fixes permanently into the AGL BSP layer (meta-agl/meta-agl-bsp/meta-raspberrypi) so future image builds produce correct boot files for RPi5 without manual SD card edits
  • Started work on the seam-stitching algorithm — researching multi-camera image alignment, overlap region detection, and blending strategies to combine the rear-camera feeds into a seamless surround view

Details

Why the camera was not working — image recipe mismatch

The camera worked in the previously built agl-ivi-demo-flutter image (Jun 25) but not in the newer agl-image-flutter-debug image (Jun 26). Comparing the two image manifests revealed the root cause immediately:

Package agl-ivi-demo-flutter agl-image-flutter-debug
rpi-libcamera ✓ present ✗ missing
pipewire-spa-plugins-libcamera ✓ present ✗ missing
pipewire-spa-plugins-v4l2 ✓ present ✗ missing

agl-image-flutter-debug is a minimal Flutter development image — it adds SSH, debug packages, and Flutter tooling, but does not pull in the camera stack. agl-ivi-demo-flutter includes camera-gstreamer in its AGL_APPS_INSTALL, which transitively pulls in rpi-libcamera and the PipeWire libcamera SPA plugin. The debug image simply does not include this dependency chain.

The correct image for camera work is agl-ivi-demo-flutter. The build was re-triggered with bitbake agl-ivi-demo-flutter after first killing a stuck BitBake server: 

# Kill hung BitBake server
kill -9 $(cat bitbake.lock)
rm -f bitbake.lock bitbake.sock

# Rebuild
bitbake agl-ivi-demo-flutter

RPi4 camera fixes — three issues in the build

Fix 1 — Missing dtoverlay for IMX219 (Camera V2)

The config.txt deployed to the SD card had no camera dtoverlay because RASPBERRYPI_CAMERA = "1" (for Camera V1 / OV5647) was never set. Since we use a Camera V2 (IMX219), the correct variable is RASPBERRYPI_CAMERA_V2. Added to raspberrypi4/conf/local.conf: 

# Enable Raspberry Pi Camera V2 (imx219)
RASPBERRYPI_CAMERA_V2 = "1"

The AGL BSP layer's rpi-config_git.bb reads this variable and appends dtoverlay=imx219 to config.txt during the deploy task. Without this line the kernel never initialises the camera sensor at boot.

Fix 2 — PROVIDES missing from rpi-libcamera recipe

The rpi-default-providers.inc in meta-raspberrypi sets: 

PREFERRED_PROVIDER_libcamera ?= "rpi-libcamera"
PACKAGE_EXCLUDE:append = " libcamera"

This tells BitBake to use the Raspberry Pi libcamera fork instead of the upstream meta-oe libcamera package. However, this only works if rpi-libcamera actually advertises itself as providing libcamera. The recipe was missing: 

PROVIDES += "libcamera"

Without this line, PREFERRED_PROVIDER_libcamera cannot resolve to rpi-libcamera, the dependency chain breaks, and the libcamera SPA plugin for PipeWire ends up absent from the image. The fix was committed to bsp/meta-raspberrypi/recipes-multimedia/rpi-libcamera/rpi-libcamera_0.5.2+rpt20250903.bb.

RPi5 first boot — two issues in the AGL image

Issue 1 — No display output / kernel logs on UART only

After reflashing correctly, the RPi5 booted (green activity LED) but the screen showed nothing after the initial firmware splash. The culprit was cmdline.txt: 

dwc_otg.lpm_enable=0 console=serial0,115200 root=/dev/mmcblk0p2 ...

Only console=serial0,115200 was set — all kernel output goes to the UART GPIO pins. There was no console=tty0, so the HDMI display received nothing from the kernel. The firmware splash (red/grey screen) appears before the kernel takes over and is unaffected, which is why that was visible but nothing else was.

The fix — add console=tty0 to the kernel command line. This was committed permanently to the AGL build via rpi-cmdline.bbappend so all future RPi5 images include it automatically.

Issue 2 — U-Boot freeze on first boot (root cause)

Even with console=tty0 added, the boot sequence froze at the U-Boot logo. Inspecting the boot partition revealed the key: 

ls /media/abdu/boot/
  Image          (27 MB  — Linux kernel)
  kernel_2712.img (680 KB — this is U-Boot, not Linux)

The RPi5 firmware (BCM2712 SoC) auto-loads a file named kernel_2712.img by default when no kernel= is specified in config.txt. In the AGL image build, this file is U-Boot — the 680 KB size is the giveaway (a Linux arm64 kernel is always 20–30 MB).

U-Boot was freezing because its boot.scr script ran: 

if test ! -e mmc 0:1 uboot.env; then saveenv; fi

On first boot uboot.env does not exist, so U-Boot attempts to write its entire environment to the FAT32 boot partition. This write hangs — most likely a timing or FAT driver issue in U-Boot 2026.01 on the RPi5's RP1 south bridge. From the outside it looks identical to a hard freeze.

The fix: tell the RPi5 firmware to load the Linux kernel directly, bypassing U-Boot entirely, by adding kernel=Image to config.txt: 

echo "kernel=Image" >> /media/abdu/boot/config.txt

With this one line, the firmware loads Image (27 MB, Linux kernel), applies the DTB overlays from config.txt, passes cmdline.txt as the kernel command line, and boots directly into Linux. U-Boot is never touched. The RPi5 booted to the AGL homescreen on the next attempt.

Build-level fixes committed to meta-agl

Both RPi5 fixes were committed permanently into the AGL BSP layer so they are applied automatically on every future build — no manual SD card edits needed.

meta-agl-bsp/meta-raspberrypi/recipes-bsp/bootfiles/rpi-config_git.bbappend

do_deploy:append:raspberrypi5() {
    # RPi5 firmware auto-loads kernel_2712.img (U-Boot) by default.
    # U-Boot freezes on first boot (saveenv hang). Boot Linux kernel directly instead.
    echo "" >> ${DEPLOYDIR}/bootfiles/config.txt
    echo "# Boot Linux kernel directly, bypassing U-Boot" >> ${DEPLOYDIR}/bootfiles/config.txt
    echo "kernel=Image" >> ${DEPLOYDIR}/bootfiles/config.txt
}

meta-agl-bsp/meta-raspberrypi/recipes-bsp/bootfiles/rpi-cmdline.bbappend

# Show kernel boot logs on HDMI display (not only on UART serial)
CMDLINE:append:raspberrypi5 = " console=tty0"

Challenges & learnings

Challenge

The RPi5 U-Boot freeze had no visible error — the screen just stopped at the U-Boot logo with no output. The only way to diagnose it was to read the boot.scr source with strings, identify the saveenv call, and cross-reference it with the known first-boot behaviour of U-Boot on FAT partitions. Serial console access would have shown the exact hang point immediately — a USB-UART adapter on the GPIO pins is now on the hardware checklist for all future boards.

Key learning

On RPi4/5, kernel_2712.img and u-boot.bin are the same file renamed — the firmware's default kernel name for BCM2712 is how AGL loads U-Boot without a kernel= line. File size is the fastest way to tell them apart: Linux arm64 kernel ≥ 20 MB, U-Boot ≤ 1 MB. When in doubt, file kernel_2712.img will say "U-Boot legacy uImage".
