IPM in Shaders, a Live Wayland Preview, and the Case for Per-Camera Parameters

Jul 14 – 20, 2026 Abdulrahman github: libcamera-dmabuf-capture@92ed4fd

This week

  • Took last week's IPM math and actually put it in the shader — replaced the old flat side-by-side composite with a real per-fragment homography warp onto a shared ground plane, so the dual-camera output is finally a true bird's-eye view
  • Used Joel's agl-presentation-egl example from wayland-cxx-scanner PR #90 to finally get the output on a window — a live Wayland preview instead of only saved snapshots, like I said I'd try last week
  • Made camera height, pitch, yaw, and the rest live-tunable with the keyboard while the preview is running — but while testing it I found a real bug: height/pitch/yaw apply to both cameras at once, which is wrong. Only the left/right distance (the 40 cm baseline) is actually independent per camera right now — the two cameras can be mounted at slightly different heights/angles in real life, and the code doesn't allow for that yet
  • Tested both ways — recorded video files and the live camera feed — and both give a correctly stitched bird's-eye view

Details

Context

Last week was the math: derive ground_to_image_H(), verify it standalone with a plain g++ build, no GPU involved. This week was putting that math where it actually does something — in the shader, on real hardware, watched live instead of guessed at from a saved PNG.

Bird's-eye view via shaders

The idea, same as last week: for every pixel of the bird's-eye-view (BEV) output, ask "if there's a real ground point here, where does it show up in the camera image?", then sample there. That's a single 3×3 homography per camera, and now it's actually running — one matrix-vector multiply and a perspective divide, entirely inside the fragment shader: 

vec3 p  = vec3(gl_FragCoord.xy, 1.0);   // this fragment IS a ground-plane point
vec3 sL = uH_L * p;                     // project into the left camera
vec3 sR = uH_R * p;                     // project into the right camera
vec2 uvL = sL.xy / sL.z;                // perspective divide -> camera uv
vec2 uvR = sR.xy / sR.z;

The two homographies (uH_L, uH_R) are built once on the CPU from camera intrinsics and each camera's position/orientation, then uploaded as uniforms — all the per-pixel GPU work is one matrix-vector multiply and a divide, so there's zero extra CPU cost per frame. Where both cameras see the same ground point, a smoothstep blend across the overlap removes the seam; where neither camera covers a point, it renders black.

(The homography-direction bug from last week — H = P*M, not inverse(P*M) — was already caught and fixed before any of this; see last week's post for the full derivation.) Matrix reference: what each variable actually does

Worth writing down precisely, since it's the part that's easiest to get lost in: the whole transform is three small matrices composed into one. Each live-tunable variable lives in exactly one of them.

M — BEV pixel → ground point

Only variable here: px_per_m (ground-sampling density).

M = | 1/r_    0     -(bev_w/2)/r_ |
    | 0      -1/r_   (bev_h/2)/r_ |
    | 0       0            0      |
    | 0       0            1      |    (r_ = px_per_m)

R — world → camera rotation

Variables here: pitch, yaw.

R = | xcam |   ← right2   (function of yaw only)
    | ycam |   ← -up2    (function of pitch and yaw)
    | zcam |   ← fwd2    (function of pitch and yaw)

t — translation (folded into [R|t])

Variables here: cam_x (= ∓baseline/2, left/right only), cam_y, h (camera height).

C = (cam_x, cam_y, h)
t = -R * C

K — intrinsics

Variables here: img_w, img_h — not a tunable key, taken from the decoded frame automatically.

K = | fx  0  cx |    fx = fy = 2714.0 * (img_w / 3280.0)
    | 0  fy  cy |    cx = img_w / 2,  cy = img_h / 2
    | 0   0   1 |

Final formula

H = K · [R | t] · M

computed as P = K·[R|t] then H = P·M, with rows 0/1 of H divided by img_w/img_h so the shader's perspective-divided (u,v) land in [0,1] directly.

Getting my output on a window, with Joel's help

I said last week it was time to get my output on the window — watching the result only through saved PNG snapshots was slow to iterate on. So this week I added an opt-in live preview window over Wayland, built directly on Joel's wayland-cxx-scanner, specifically the agl-presentation-egl example from PR #90 — same render-to-texture-then-composite pattern (the FBO's color attachment gets sampled by a full-screen quad pass, since GLES2/3 has no glBlitFramebuffer), same wp_presentation feedback for real commit-to-light latency numbers.

Getting it working on the actual AGL compositor surfaced a real upstream issue along the way: the window registers itself as the compositor's persistent background surface via agl_shell.set_background(), and when my app exited, agl-compositor itself crashed — coredumpctl + gdb traced it to a libweston assertion ("empty scene graph at repaint") in the background-surface teardown path. The protocol has no "unset background" request, so this looks like a genuine upstream gap, not something I can fix from the client side. For now I worked around it: loop the input video on EOS instead of ever letting the process exit, which sidesteps the crash entirely since it only triggers on exit — enough to keep testing productive while a real fix would need to happen upstream.

Live-tunable parameters, and a bug I found while using my own tool

Height, pitch, yaw, baseline, forward offset, and ground-sampling scale are all adjustable with dedicated keys while the preview runs, rebuilding and re-uploading the homographies on the fly. Actually sitting there tuning it live is what made a design mistake obvious: height/pitch/yaw all live in one shared parameter set used to build both cameras' homographies, differing only in the X offset. That's correct for the baseline itself — the two cameras really are 40 cm apart and that distance is exactly what's modeled — but it's wrong for height/pitch/yaw, which on a real rig can differ slightly per camera just from mounting tolerance. Right now there's no way to nudge only the right camera's pitch half a degree to correct for a slightly crooked mount. That needs independent left/right parameter sets, not one shared set — on the list for next week.

Testing — recorded video and the live camera

Verified the full pipeline both ways: against recorded test footage (useful for repeatable, controlled testing of the stitching math itself) and against the live IMX219 camera feed (the real end-to-end path). Both produce a correctly stitched, live-tunable bird's-eye view.

Challenges & learnings

Challenge

The shared-parameters bug wasn't obvious from reading the code — it only became clear by actually using the live-tunable keys while watching the preview and asking "what if the two cameras aren't mounted identically?" A good reminder that interactive testing surfaces design gaps that a code read-through alone doesn't.

Key learning

Verify math before it ships, whether that's a standalone unit test for a homography direction or a debugger attached to a live crash. Both the IPM math bug and the compositor crash were caught by getting hard evidence first, not by trusting the first plausible-looking fix.
