Building the App Inside AGL: Every Problem and Every Change

Sep 22 – Sep 28, 2026 Abdulrahman

This week

  • Wrote the Yocto recipes for the camera application in meta-agl-demo: agl-backup-camera (the library and a CLI test tool) and flutter-surround-view, the AGL app entry point built on the agl-app-flutter template
  • Got the whole agl-ivi-demo-flutter image for the Raspberry Pi 5 building on AGL master with the app inside, working through every build failure in the order it showed up
  • Moved the Flutter side to meta-flutter's v3 generation, the only one with the platform-view API (ivi-homescreen-shared) the app needs, and fixed what v3 and AGL's layers disagree on
  • Kept every machine-local setting out of local.conf and out of the AGL layers: one site.conf, one repo local manifest and one small local layer
  • Wrote down every change needed to build the app with AGL, where each one lives today, and the questions for my mentors before anything goes to Gerrit

Details

Why this post

Before I push anything to AGL's Gerrit I want my mentors to see the whole picture: what it took to build the app inside the AGL image, which of those changes belong to the app, which belong to AGL's layers, and which are only workarounds on my machine. So this week is only about the build. Every problem is written the same way: what failed, why, the fix, and where the fix lives now.

The target is agl-ivi-demo-flutter for raspberrypi5, from AGL master, with the build folder generated by: 

source meta-agl/scripts/aglsetup.sh -f -m raspberrypi5 -b raspberrypi5 \
    agl-app-framework agl-demo agl-devel agl-flutter \
    agl-package-management agl-pipewire agl-selinux

1. The recipe itself

  • Wrong build system. The first recipe inherited meson. The project builds with CMake, so it inherits cmake pkgconfig.
  • A typo in DEPENDS. virtual/libgm instead of virtual/libgbm.
  • Submodules not fetched. The repository has two (stb and wayland-cxx-scanner), so SRC_URI uses gitsm://, which reads .gitmodules.
  • No license. The repository had no LICENSE file, so the license check could not pass. I added Apache-2.0 and put its real md5 in LIC_FILES_CHKSUM.
  • Missing build dependencies. CMakeLists.txt runs its pkg_check_modules(... REQUIRED) calls at the top, for every target. So even the Flutter recipe, which only builds the platform view, has to list GStreamer in DEPENDS.

2. After repo sync: the tree moved under me

  • No more rpi-libcamera and rpicam-apps. meta-raspberrypi dropped its own libcamera fork and now only adds a libcamera_%.bbappend that enables the Pi pipelines on the upstream recipe. The recipe depends on libcamera now.
  • ffmpeg and rpidistro-ffmpeg tried to install the same files. A pre-existing AGL issue, not caused by the app.
  • Kuksa needs a newer Rust. kuksa-databroker needs rustc 1.96 and the tree has 1.94.1, so the agl-kuksa-val feature is left out of the build.
  • A stale Flutter pub cache. flutter-ics-homescreen failed with flutter pub get --enforce-lockfile --offline (exit 65). meta-flutter keeps the cache archive name in a marker file, PUB_CACHE_ARCHIVE, and reuses the archive without checking that the app source changed, so it restored packages from older sources. bitbake -c cleansstate flutter-ics-homescreen fixed it.

3. The big one: AGL's Flutter shell has no platform views

The app shows the GPU output through an ivi-homescreen platform view (libbev_view.so). Its Dart build hook always configures with -DENABLE_IHS_PV=ON, which needs the shell's shared/ platform-view API: 

CMake Error at CMakeLists.txt:257 (message):
  ENABLE_IHS_PV: no build of ihs_shared for this target

AGL's manifest pins meta-flutter at 450ea5b3, the v2 generation, which has no shared/ at all. meta-flutter's v3 generation (from 8af2ba88, "roll to Flutter 3.47.1 and add ivi-homescreen v3") adds an ivi-homescreen-shared package, which the app's CMake already finds through pkg-config. I moved to v3 with a repo local manifest, so AGL's own manifest is untouched: 

<!-- .repo/local_manifests/local_meta-flutter-v3.xml -->
<remove-project name="meta-flutter/meta-flutter"/>
<project name="meta-flutter/meta-flutter" path="external/meta-flutter" remote="github"
         revision="5d4ba958810ba31693a461d7a5757bb6d5cc58ca" upstream="master"/>

That one step brought its own problems:

  • License strings this bitbake rejects. Several v3 recipes write LICENSE = "X AND Y", which this bitbake treats as a fatal parse error (it wants &). None of those recipes are needed, so the sample apps and test recipes are masked with BBMASK. A bbappend in meta-agl-flutter targets one of the masked samples, and a bbappend without its recipe is also fatal, so it is masked too. Two recipes the image does need, libwebrtc and rive-text, get their LICENSE rewritten in a local bbappend.
  • The pinned shell was too old. meta-flutter 5d4ba958 pins ivi-homescreen at 131cbc37. The platform view needs 4bb31fda or later (a release-fence fd leak and the Vulkan backend never handing back a release fence). Upstream meta-flutter later rolled to 3d7a9671 in a commit that only changes two hashes, so I override exactly those two: HOMESCREEN_COMMIT and PLUGINS_COMMIT.
  • The compositor option on the wrong recipe. Platform views are only compiled in with BUILD_COMPOSITOR. I first set it on ivi-homescreen, and by editing a file inside meta-agl directly, which I reverted. AGL's shell is flutter-auto: PACKAGECONFIG:append:pn-flutter-auto = " compositor".
  • The app's Dart constraint. The app asked for Dart ^3.11.1, newer than AGL's Flutter at the time, so I lowered it to ^3.10.0. Nothing in the app needs 3.11.
  • The home screen no longer resolved its packages. With v3, flutter-ics-homescreen (which sets PUBSPEC_IGNORE_LOCKFILE = "1") pulled objective_c 9.6.2, whose native assets need a newer code_assets than the 1.1.0 its dependency_overrides pin. Pinning objective_c: 0.5.0 failed because that version doesn't exist on pub.dev. A local bbappend now adds objective_c: 9.0.0 to its dependency_overrides.

4. Building the platform view inside Yocto

  • CMake found my host shell. With EXTERNALSRC pointing at my checkout, CMake probed ../ivi-homescreen, my x86 build of the shell. The recipe now fetches my local branch through git, so the build only sees the sysroot's ivi-homescreen-shared.
  • The Dart hook needs OE's toolchain. The recipe uses meta-flutter's flutter-app-native class, which puts a cmake wrapper with OE's toolchain file on PATH for the hook. (AGL's flutter-app-plugins is an older copy that appends --target-platform a second time.)
  • libc++ against libstdc++. flutter-app-native builds hooks with clang's libc++ (std::__1::). libcamera is built with libstdc++ (Camera::id[abi:cxx11]()), and its C++ API passes std::string and std::function, so the two can never link. The recipe removes -stdlib=libc++ -rtlib=compiler-rt -unwindlib=libunwind for itself only. The shell stays on libc++, which is fine because the view talks to it only through ihs_shared's C interface.
  • A stale Flutter SDK stamp. The flutter tool decided its own snapshot was stale and tried to download from pub.dev, and the network is closed in do_compile. Same family as the pub-cache bug. bitbake -c clean flutter-surround-view fixed it.
  • The library was not found at runtime. Flutter records the native asset by bare name (["absolute","libbev_view.so"]), so the engine's dlopen uses the normal search path, and the file sits in data/flutter_assets/native_assets/linux/. The recipe installs /etc/default/surround_view with an LD_LIBRARY_PATH. AGL's app service already reads that file.

5. libcamera on the Pi 5

The image built, but cam -l found no camera. AGL's libcamera 0.6.0 (from meta-openembedded) looks for the CFE media entities with hyphens (rp1-cfe-fe-image0), and the Pi 5 kernel 6.18 registers them with underscores (rp1-cfe-fe_image0). The Raspberry Pi fork of libcamera uses underscores. Building the fork, and enabling both cameras, is an override in site.conf, kept opt-in instead of forcing a fork on every Pi 5 build: 

SRC_URI:pn-libcamera = "git://github.com/raspberrypi/libcamera.git;protocol=https;nobranch=1;tag=v0.6.0+rpt20251202"
SRCREV:pn-libcamera  = "f0e40f1c50bd0afe65727d6e407d0dcb42666ada"
RASPBERRYPI_CAMERA_V2 = "1"
RPI_EXTRA_CONFIG = "\ndtoverlay=imx219,cam0\ndtoverlay=imx219,cam1\n"

Which libcamera branches I tried, and what each one does on the Pi 5, is in week 19.

6. Settings the app needs to run (not build problems, but part of the change set)

  • Home screen config. flutter-auto v3 reads [view.shell.window] type = "BG" and silently ignores v2's window_type = "BG", so the home screen never became the background and the screen stayed black. A local bbappend ships the config in v3 format.
  • Apps as plain xdg windows. v3 tries agl-shell whenever the compositor offers it, and only the home screen may bind it. A systemd drop-in runs AGL's Flutter apps with --shell xdg.
  • Show new windows on activation. activate-by-default=true in the compositor's weston.ini, through a bbappend on weston-ini-conf (named without _%, because that recipe has no version and bitbake rejected the wildcard).
  • Free the cameras. wireplumber@video-capture keeps every camera open. I stop it by hand; it is not in a recipe yet.

7. My machine

A full image build ran my PC out of memory (the OOM killer closed my editor), so site.conf limits it to 4 bitbake threads and -j 4, with -j1 for the cross-canadian gcc and binutils, and inherits rm_work. Long builds run as their own service so a kill doesn't lose the session.

Questions for my mentors before Gerrit

  1. meta-flutter v3. The app needs it, and AGL master pins v2. Is moving AGL to v3 planned, or should the app have a v2 path?
  2. The libcamera fork. Should the Raspberry Pi fork go into meta-raspberrypi or meta-agl-bsp behind a MACHINE_FEATURES flag, or should the naming mismatch be reported upstream first?
  3. Which layer. meta-agl-demo (where the recipes are now) or meta-agl-devel?
  4. The v3 fixes. The home screen config format, --shell xdg and activate-by-default are needed by any v3 app, not only mine. Should they go to meta-agl-flutter as separate changes?
  5. OpenCV. The calibration library (week 19) needs OpenCV from meta-oe. Is a new dependency of that size acceptable in a demo image?

On my side, before any review: push the app repository to GitHub, point both recipes at it with a pinned SRCREV, add RECIPE_MAINTAINER, and use one name consistently for the recipe, PUBSPEC_APPNAME and AGL_APP_ID.
