Week 2: Verifying the Camera DMA-BUF Pipeline

Jun 2 – Jun 8, 2026 Abdulrahman
Project: libcamera-dmabuf-capture

This week

  • Wrote a standalone C++ tool using the libcamera API to open the IMX219, configure NV12 at 1640×1232 (2×2-binned full-sensor mode), and capture a frame — confirming the camera hands back a real kernel DMA-BUF file descriptor
  • Cross-compiled the tool from the host using the Yocto toolchain already in sysroots-components, with no image rebuild or reflash needed — worked around broken toolchain symlinks left by rm_work
  • Added a 30-frame AE/AWB warmup — the IMX219 first frame is black until the exposure feedback loop converges, so we skip 30 frames before saving
  • Fixed zoomed image: 1280×720 is a partial-readout sensor mode on the IMX219 that crops the sensor centre. Switching to 1640×1232 — the 2×2-binned full-sensor mode — reads the entire 3280×2464 array and gives the correct wide-angle field of view
  • Fixed corrupted raw output: the camera aligns rows to 64 bytes (stride 1664, not 1640), so writing the full buffer directly produces diagonal lines in ffplay. Fixed by stripping the padding when saving — writing only the valid width bytes per row

Details

Why a standalone test first

The full backup camera pipeline will be: camera / DMA-BUF / GPU texture / GLSL shader / Wayland surface / AI overlay. Before writing any of the GPU or display code, I needed to answer one question: does libcamera on this AGL image actually give me a kernel DMA-BUF fd I can later pass to EGL?

The answer turns out to be yes, but getting there took most of the week, mostly because of the cross-compilation setup rather than anything in libcamera itself.

Cross-compilation without rebuilding the image

The AGL image doesn't have a C++ compiler installed, so native compilation on the RPi4 isn't an option without adding tools-sdk to the image features and reflashing (which takes a couple of hours). Instead, I cross-compile on the host using the aarch64-agl-linux-g++ compiler that Yocto already built into raspberrypi4/tmp/sysroots-components/.

The problem is that this build had INHERIT += "rm_work" set, which deletes each recipe's work directory after building it. The compiler binary itself survives, but it was compiled with hard-coded paths pointing into the now-deleted Yocto sandbox. All the symlinks in the gcc libexec/ directory are broken, including the bare as the driver looks for when it needs to assemble.

The workaround I landed on: create a temporary directory with bare-named symlinks (as, ld, etc.) pointing to the real cross-tools in binutils-cross-aarch64, prepend it to PATH, and also set GCC_EXEC_PREFIX and COMPILER_PATH so the driver finds cc1plus. Then the whole thing works without touching the Yocto build.

The DMA-BUF fd

After getting the binary on the board and running it, the output looks like this: 

[capture] camera: /base/soc/i2c0mux/i2c@1/imx219@10
[capture] warming up AE/AWB (30 frames)...
=== Frame captured (frame 31) ===
  Width      : 1640
  Height     : 1232
  Stride     : 1664
  PixelFormat: NV12
  Planes     : 2
  Plane[0]:  fd=15  offset=0  length=2049920
  Plane[1]:  fd=15  offset=2049920  length=1024960
[capture] raw frame saved to /tmp/frame.raw (1640x1232 NV12, stride=1664)

fd=15 is the interesting part. You can confirm it's a real kernel DMA-BUF object (not just a regular file or mmap region) by looking at what /proc/<pid>/fd/15 points to while the program is paused. It shows /dmabuf:, which is the kernel's way of tagging a DMA-BUF handle in the fd table. That fd is what gets passed to EGL in the next stage to create a GPU texture without any pixel copying.

The raw frame saves correctly. Copying it off the board and playing it back with ffplay confirms it's a real wide-angle image: 

scp root@<rpi-ip>:/tmp/frame.raw .
ffplay -f rawvideo -pixel_format nv12 -video_size 1640x1232 frame.raw

The Sony IMX219 sensor

The camera module uses the Sony IMX219, an 8-megapixel sensor (8.08 MP) with a maximum resolution of 3280×2464 pixels. It's the same sensor inside the official Raspberry Pi Camera Module V2 and many Jetson Nano boards.

The IMX219 isn't a single-mode sensor. It has several native hardware readout modes, each with a different crop, binning level, and maximum framerate:

Mode Resolution FOV ~FPS Notes
Full res 3280 × 2464 Full ~15 All pixels read, no binning
2×2 binned 1640 × 1232 Full ~40 Entire array, 4 pixels to 1 output pixel - used here
Partial crop 1920 × 1080 Cropped ~30 Reads centre of array only
Partial crop 1280 × 720 Cropped ~60 Centre crop, zoomed appearance

The first time I ran the tool at 1280x720, the image was noticeably zoomed in. Objects appeared larger than they should and the edges of the room were cut off. The lens wasn't zoomed; the sensor mode was. libcamera selects sensor modes based on the requested output size. At 1280x720 it picks the dedicated 60fps mode that physically reads only the centre portion of the array at full pixel density, a hardware crop, not a downscale.

The fix is to request a size that makes libcamera choose a full-readout mode. 1640×1232 selects the 2×2-binned mode: the sensor reads the entire 3280×2464 array and combines every 2×2 block of pixels into one output pixel. Result: correct wide-angle field of view at ~40fps, more than enough for a backup camera.

Stride and the corrupted raw file

After switching to 1640x1232, the saved raw file showed only diagonal lines in ffplay, a classic sign of a stride mismatch. Camera drivers align each row to a memory boundary for DMA efficiency. For NV12 at width 1640, the driver pads each row to 1664 bytes (the next multiple of 64). That's 24 bytes of padding at the end of every row.

The original code wrote plane.length bytes as a contiguous block, padding included. ffplay reads a packed NV12 file and assumes no padding, so each row it reads starts 24 bytes into the next row's data, and the whole image shifts diagonally. The fix is to loop over rows and write only the valid width bytes per row, stepping by stride bytes to skip the padding: 

for (unsigned int row = 0; row < rows; ++row)
    out.write(src + row * stride, width);  // stride=1664, width=1640

Challenges & learnings

Challenge

The Yocto cross-toolchain had all its internal symlinks broken by rm_work. There's no obvious error, the compiler just silently calls the host x86 assembler and produces the wrong binary. Required reading through gcc's subprogram search logic to understand why and find the fix.

Key learning

Camera sensor modes are hardware-level choices, not software crops. The IMX219's 1280x720 mode physically reads fewer pixels from the sensor centre, you can't override that with a software control. To get the full field of view, request a size that maps to a full-readout mode (1640x1232 = 2x2 binned full array). Also: stride != width - always strip row padding when writing packed raw files.
